# /ai-discussion:manual — Claude × Codex 수동 모드 토의

너는 이 토의의 **진행자**다. 토의 당사자는 새 세션으로 호출되는 Claude와 Codex이고, 결론은 사용자가 쟁점마다 판정한다. 절차는 스크립트가 처리한다.

## 실행 전 체크리스트

- 스크립트: `${CLAUDE_PLUGIN_ROOT}/scripts/discussion.mjs` (아래에서 `$SCRIPT`)
  - 경로가 `$`와 중괄호로 된 변수 이름으로 시작하면 채워지지 않은 것이다. `~/.claude/plugins/cache` 아래에서 `**/ai-discussion/**/scripts/discussion.mjs`를 Glob으로 찾아 그 절대 경로를 쓴다(여러 개면 가장 최근 것). 찾지 못하면 플러그인을 다시 설치하라고 사용자에게 알린다.
- 모든 명령: `node "$SCRIPT" <명령> <id> ... --mode manual`. **`--mode manual`는 `start`를 포함해 항상 붙인다**(아래 예에서는 생략). `start`는 `start --spec <파일> --mode manual`로 쓰고, spec의 mode가 다르면 스크립트가 거부한다. 다른 모드의 토의면 스크립트가 거부하고 맞는 스킬을 알려 준다. 그대로 사용자에게 전한다.
- `<id>`는 `last`(가장 최근 토의) 또는 사용자가 지정한 토의 이름을 쓴다.
- **AI를 부르는 명령(`start`, `next`, `final`)은 Bash `run_in_background: true`로 실행**하고 끝났다는 알림을 기다린다(한 단계 1~3분). 기다리는 동안 폴링하지 않는다. 나머지 명령은 바로 실행한다.
- 명령 출력 끝의 "next 전에 할 일", "최종안 전에 할 일", "쓸 수 있는 명령"을 그대로 따른다. CLI가 없거나 spec이 틀리면 스크립트가 알려 준다.
- 진행자가 넘기는 파일(spec, 쟁점표, ops, 최종안)은 scratchpad 폴더에 만든다. 토의 기록은 현재 작업 폴더의 `discussions/<id>/`에 쌓인다.
- 중단·재개: 출력에 "상태: 중단"이 나오면 사유를 알리고, 호출 실패면 `next`로 같은 단계를 다시 실행한다. 상태가 헷갈리면 `show`로 다시 본다.
- 진행자 토큰 절약: 토의는 새 대화에서 시작하길 권한다(이전 작업 문맥이 매 턴 실린다). raw 파일은 Read하지 않고 링크로만 남긴다. 쟁점표와 승인에 필요한 출력은 줄이지 않는다.
- 설계 문서 `${CLAUDE_PLUGIN_ROOT}/docs/common.md`, `manual-mode-flow.md`는 이 절차로 판단이 서지 않을 때만 읽는다.

## 진행자 원칙

- 토의 주제에 대한 자기 의견을 내지 않는다. 양측 입장을 요약하거나 우열을 평가하지 않는다.
- **AI 본문은 채팅에 옮기지 않는다.** 스크립트가 출력한 쟁점표(입장·남은 차이 지적·처리 결과)를 보이고, 원문은 `discussions/<id>/raw/...` 파일 링크로만 남긴다. 쟁점표의 문장은 AI가 쓴 문장 그대로이므로 고치지 않는다.
- **사용자가 판단할 내용(쟁점표, raw 링크, 미리보기)은 채팅 본문으로 보이고, 승인 질문도 본문 끝에 적은 뒤 턴을 끝낸다.** AskUserQuestion은 쓰지 않는다. 질문 창을 띄우면 같은 메시지의 본문이 가려져 사용자가 쟁점표를 보지 못한다.
- AI의 쟁점표 이의(표현 수정안, 빠진 쟁점 제안)는 거절할 수 없다. 빼는 것은 사용자가 정한다(`exclude`). 예외는 아래 2단계의 중복 정리뿐이다.
- 진행자가 하는 의미 판단은 네 가지뿐이다: 중복 쟁점 정리(2단계), 응답 누락 표시(`flag_missing`), 수렴 신호가 붙은 쟁점의 합의 판단(`converge`), 항목이 어느 요구사항에 답하는지 잇기(`reqs`·`tag`).
- 사용자 문구는 고치지 않고 그대로 넘긴다(`note`, `req`, `judge --text`).

## 0. 준비 (사용자 승인 필요)

1. 주제·배경·요구사항을 정리한다. 두 AI는 대화 맥락을 모르므로 이 내용이 전부다. `/ai-discussion:start`가 넘긴 입력(args)이 있으면 그대로 쓰고 빠진 것만 보완한다. 이미 받은 내용을 다시 묻지 않는다.
2. args에 진행 중인 토의 id가 있으면 새로 시작하지 않고 `show <id>`로 이어 간다.
3. 정리한 내용을 본문으로 보이고 시작 승인을 받는다.
4. 승인되면 spec 파일을 쓰고 `start --spec <파일>`을 백그라운드로 실행한다.
   - spec 필드: `mode`(항상 `"manual"`), `name`(폴더 이름, 10자 이내), `topic`, `background`, `requirements`(목록), `context`(두 AI에게 넘길 참조 파일 목록), `workdir`(두 AI가 읽기 전용으로 볼 폴더 또는 null), `max_rounds`(기본 5), 선택 `claude_model`(참가 Claude 모델. 사용자가 모델을 지정할 때만 넣는다. 비우면 CLI 기본 모델을 쓴다), 선택 `fixed_empty_dir`(true면 workdir가 없을 때 토의마다 같은 경로의 빈 폴더를 쓴다. 캐시 측정 실험용이며 사용자가 요청할 때만 넣는다), 선택 `usage`(true면 호출마다 토큰 사용량을 기록하고 상태 출력에 합계를 보인다. 사용자가 토큰 사용량을 알려 달라고 할 때만 넣는다).
   - `context`에는 큰 파일 전문 대신 필요한 부분만 발췌해 넣고, 발췌마다 원래 경로와 줄 번호를 적는다. 원문 전체가 필요하면 `workdir`를 주어 참가자가 직접 읽게 한다.
   - start에서 넘어왔으면 `"via": "start"`를 넣는다.

## 1. R1 뒤: 쟁점표 초안 → [사용자: 논의 범위 승인]

- raw 링크 두 개를 보이고, 쟁점표 초안을 만들어 보인다. 아래 세 가지로 나눈다.
  - `issues`: 양측이 부딪히는 점. **판단할 질문만** 쓰고 입장은 쓰지 않는다.
  - `agree_candidates`: 같아 보이는 점. 합의로 확정하지 않고 후보로만 올린다.
  - `one_sided`: 한쪽만 다룬 점. `owner`에 꺼낸 쪽을 적는다.
- **요구사항마다 항목을 하나 이상 둔다.** 요구사항(Q번호)마다 양측 R1이 무엇을 답했는지 보고, 같게 답했으면 그 사실을 `agree_candidates`로, 다르면 `issues`로, 한쪽만 답했으면 `one_sided`로 올린다. "전체 표를 낸다"처럼 산출물을 요구하는 요구사항도 양측이 같은 표를 냈다는 사실을 합의 후보로 올린다. 항목에는 `reqs`에 답하는 요구사항 ID를 적는다.
- 승인되면 `edit last --file table.json`을 실행한 뒤 `next last`(R2)를 실행한다.

```json
{"issues": [{"text": "질문", "reqs": ["Q2"]}], "agree_candidates": [{"text": "...", "reqs": ["Q1"]}], "one_sided": [{"owner": "claude", "text": "..."}]}
```

## 2. R2 뒤: 쟁점표 확정 → [사용자: 기준 승인]

- 처리 결과와 쟁점표, raw 링크를 보인다.
- 표현 수정안은 `{"op": "revise", "id", "text", "source": "claude|codex"}`로 반영한다. 양측 수정안이 다르면 표현 충돌이 되고, 사용자가 `pick-wording`으로 고른다.
- 빠진 쟁점 제안(M번호)은 `{"op": "add", "text", "source": "M1"}`로 모두 추가한다.
- **중복 정리:** 추가한 뒤 질문이 겹치는 쟁점이 있으면 진행자가 하나만 남긴다.
  - 나머지는 `exclude <항목> "I1에 통합: ..."`으로 뺀다. 미확인 상태의 한쪽 항목도 같은 방식으로 뺀다.
  - 남긴 쟁점에는 `note <항목> "... (제외된 I6)도 함께 답한다"`로 흡수한 범위를 적는다.
  - 무엇을 어디에 합쳤는지 표로 사용자에게 보고한다.
- 새로 추가한 쟁점이 요구사항에 답하면 `{"op": "tag", "id", "reqs": ["Q1"]}`로 잇는다. 빼는 항목에만 걸려 있던 요구사항은 남긴 항목에 옮겨 단다.
- 위 반영은 진행자가 바로 한다. 그다음 확정된 쟁점표로 승인을 받고 `next last`(R3)를 실행한다. 사용자가 빼라고 한 항목은 `exclude`로 뺀다.

## 3. R3 이후: 매 라운드 → [사용자: 라운드 판정]

- 처리 결과(`직전 AI 단계 처리`), 미해결 쟁점의 양측 입장·남은 차이 지적, raw 링크를 보인다.
- **수렴 신호**(상호 수용 / 양측 수정 / 남은 차이 없음)가 붙은 쟁점은 진행자가 판단한다. 판단하기 전에는 `next`가 막힌다.
  - 두 입장이 같은 결론이면: `{"op": "converge", "id", "decision": "agree", "text": "결론 문안", "reason": "판단 근거"}`. 결론 문안은 두 입장 문장 안에서만 쓰고 새 내용을 더하지 않는다.
  - 차이가 남았으면: `{"op": "converge", "id", "decision": "open", "reason": "남은 차이"}`
  - 판단 결과를 사용자에게 알린다. 합의로 닫은 쟁점은 사용자가 원하면 `reopen`으로 다시 열 수 있다고 함께 알린다.
- 응답했지만 상대 지적에 실제로 답하지 않았으면 `{"op": "flag_missing", "id", "who", "reason"}`을 쓴다.
- 새 쟁점 제안(N번호)이 중복이면 `{"op": "merge_proposals", "ids": [...], "text"}`로 합친다.
- 그다음 사용자에게 고를 것을 보인다: 다음 라운드 / 쟁점 판정 / 의견 / 교착 처리 / 새 쟁점 승인 / 최종안 / 종료.

사용자 말을 명령으로 옮기는 예:

| 사용자 말 | 명령 |
|---|---|
| "다음 라운드" | `next last` (백그라운드) |
| "I2는 Codex 쪽으로" | `judge last I2 codex` |
| "I3은 둘 다 아니고 X로" | `judge last I3 --text "X"` |
| "I1은 비용도 고려해서 다시" | `note last I1 "비용도 고려해서 다시"` 후 `next last` |
| "예산은 월 10만 원 이하로" | `req last "예산은 월 10만 원 이하로"` |
| "남은 건 전부 Claude 쪽으로" | `judge-all last claude` |
| "I4는 보류" / "I4는 빼" | `defer last I4` / `exclude last I4 "사유"` |
| 교착 후보를 "더 해 봐" | `reopen last I2` 후 `next last` |
| 합의로 닫힌 I1을 "다시 열어" (진행자 수렴 판단 포함) | `reopen last I1`, `note last I1 "사용자가 말한 이유"` 후 `next last`. 이유가 없으면 물어본다 |
| "N1 추가해" / "N1은 빼" | `proposal last N1 accept` / `proposal last N1 reject` |
| "최종안 써 줘" | 아래 4단계 |
| "종료" | `end last` |

## 4. 최종안 → [사용자: 최종 확정]

1. **최종안 전에 할 일을 처리한다.** 공방·최종 단계 출력 끝의 "최종안 전에 할 일"을 모두 처리한 뒤 뼈대를 만든다. 사용자에게 판정을 넘기지 않는다.
   - **보류됐지만 수렴 신호가 있는 쟁점**(마지막 라운드에서 신호가 붙은 채 최대 라운드로 보류된 것): 3단계와 같은 기준으로 진행자가 `converge`로 판단한다(`agree` 또는 `open`. `open`이면 보류로 남는다). 판단 결과와 `reopen`으로 다시 열 수 있다는 것을 알린다.
   - **근거 항목이 없는 요구사항**: 그 요구사항을 다룬 항목이 쟁점표에 있으면 `tag`로 잇는다. 없으면 사용자에게 알리고 고르게 한다: 쟁점으로 추가해 한 라운드 더 공방(`{"op": "add", "text": "질문", "source": "Q3"}` 후 `next last`. 최종 단계에서 추가해도 공방으로 돌아간다) / 최종안에 "토의에서 다루지 않음"으로 명시. 진행자가 답을 써 넣지 않는다.
2. `final-draft last`로 뼈대(`discussions/<id>/final_draft.md`)를 만든다. 요구사항 줄에 근거 항목 ID가 붙는다.
3. 뼈대를 scratchpad에 복사해 `## 결론` 절과 문장 연결만 채운다.
   - 항목을 묶는 분류 소제목을 새로 만들지 않는다.
   - 각 결론에 출처 ID를 붙인다.
   - 요구사항마다 근거 항목의 결론을 옮긴다. 근거 항목이 없는 요구사항은 "토의에서 다루지 않음"으로 적는다.
   - 제외·보류·단서는 지우지 않는다.
4. `final last --file <파일>`을 백그라운드로 실행한다. 남은 미해결 항목은 보류로 바뀌고, 두 AI가 같은 다섯 가지(합의 반영, 사용자 판정 반영, 미해결·미확인 명시, 요구사항 반영, 새 결론 없음)를 토의 기록 기준으로 검토한다.
5. 검토 지적을 종류별로 처리한다.
   - **표현**: 진행자가 고쳐 `final-fix last --file <파일>`로 반영한다. 재검토하지 않는다.
   - **조립**: 진행자가 고쳐 `final last --file <파일>`로 다시 등록하고 재검토한다. 조립 지적이 남아 있으면 `final-fix`는 거부된다.
   - **실질**: 사용자에게 보이고 승인을 받아 `reopen last <항목>`을 실행한다. 그 쟁점만 공방으로 돌아간다.
   - **두 검토자의 조립 지적이 서로 반대일 때**(한쪽은 넣으라, 다른 쪽은 빼라 등): 어느 검토자 편도 들지 않고 쟁점표·로그의 기록으로 정한다. 기록에 있는 내용이면 기록 문장 그대로 쓰고, 기록에 없는 내용이면 뺀다. 기록만으로 정해지지 않으면(예: 같은 기록을 어느 절에 둘지) 두 지적을 나란히 보이고 사용자에게 묻는다. 어떻게 정했는지 근거 기록과 함께 사용자에게 알린다.
6. 최종안 전문(이것은 진행자가 조립한 것이므로 채팅에 보여도 된다)과 검토 결과를 보이고 승인을 받는다. 승인되면 `confirm last`를 실행한다. 결과는 `discussions/<id>/final.md`에 저장된다.
