# 사용자 판정 모드: 쟁점 중심 토의 흐름

- 상태: 구현·dry-run 검증 완료, 스킬 작성과 실제 CLI 확인은 남음 (2026-10-26)
- 범위: 사용자 판정 모드만. AI 자동 합의 모드는 [consensus-mode-flow.md](consensus-mode-flow.md)를 따른다.
- 공통 규칙(파일 구성, 응답 파싱, 재시도, 호출 실패, 저장·재개, dry-run)은 [common.md](common.md)를 따른다.

## 목표

매번 전체 답변을 다시 쓰는 방식 대신, 초기 답변에서 쟁점을 뽑아 쟁점별로만 공방한다. 토의 대상은 이견으로 좁히되, 각 이견의 근거와 해결 과정을 보존한다.

## 역할

| 주체 | 맡는 일 |
|---|---|
| 사용자 | 시작 승인, 논의 범위 승인, 기준 승인, 라운드 판정, 최종 확정 |
| 진행자 (토의를 호출한 Claude Code 세션) | 주제·배경·요구사항 정리, 쟁점표 작성·갱신, 사용자의 말을 명령으로 옮김, 쟁점표와 원문 링크를 보여 줌, 수렴 판단, 최종안 조립 |
| 스크립트 (discussion.mjs) | AI 호출, 상태 저장, 응답 파싱, 절차 규칙 적용, 로그 기록 |
| Claude / Codex (새 세션) | 토의 당사자. 자기 입장만 직접 쓰고, 반박하고, 쟁점별 입장을 표시함 |

진행자 원칙:
- 토의 주제에 대한 자기 의견을 내지 않는다.
- 양측 입장을 요약하지 않는다. 입장은 각 AI가 직접 쓴다.
- AI의 쟁점표 이의를 거절할 수 없다.
- 의미 판단은 두 가지뿐이다. "반박에 실제로 답했는가"를 표시하는 것, 그리고 스크립트가 수렴 신호를 붙인 쟁점이 실제로 합의에 이르렀는지 판단하는 것(아래 "수렴 판단"). 내용의 우열은 평가하지 않는다.
- 진행자가 넘긴 쟁점표와 최종안은 log.md에 그대로 남긴다.

스크립트 원칙: 절차만 처리한다. "새 근거가 없다", "같은 주장의 반복이다"처럼 의미를 판단해야 하는 일은 하지 않는다.

## 진행 흐름

```
0. 준비         진행자: 주제·배경·요구사항 → [사용자: 시작 내용 승인] → start
1. R1           두 AI: 독립 답변
2. 쟁점표 초안   진행자: 쟁점(질문만) / 합의 후보 / 한쪽만 다룬 항목
                → [사용자: 논의 범위 승인]
3. R2           두 AI, 항목마다:
                 · 쟁점: 표현 확인(정확 / 수정안+이유) → 유효하면 자기 입장·근거 + 첫 반박
                 · 합의 후보: 확인 / 이의(이유)
                 · 상대만 다룬 항목: 동의 / 반대 / 근거 부족 / 무관(사유)
4. 쟁점표 확정   진행자: 이의 반영 (거절 불가, 충돌하는 수정안은 둘 다 제시)
                 · 합의 후보 이의 → 쟁점, 한쪽 항목 → 4분류대로 이동
                → [사용자: 기준 승인]
5. R3~ (반복)   두 AI, 미해결 쟁점마다:
                 · (표현이 바뀐 쟁점) 기존 반박이 아직 유효한지
                 · 답하는 반박 / 수용·반박과 근거 / 유지(hold)·변경(change)·철회(withdraw)
                 · 새 쟁점 제안 (근거 + 결론에 미치는 영향, AI당 최대 2개)
                스크립트: 철회 → 종료, 2연속 유지 → 교착 후보, 상호 수용·양측 수정·남은 차이 없음 → 수렴 신호
                진행자: 수렴 신호 판단(합의로 닫기 / 계속), 응답 누락 표시, 새 쟁점 중복 정리
                → [사용자: 라운드 판정]
                   쟁점 판정 / 의견 / 교착 처리(추가 공방·보류·판정) / 새 쟁점 승인 / 최종안
6. 최종안        스크립트: 최종안 뼈대(final-draft) → 진행자: 결론 절과 문장 연결만 채움
                두 AI 검토: 합의 반영 / 사용자 판정 반영 / 미해결·보류 명시 / 토의에 없던 결론 추가 여부
                 · 지적마다 표현·조립·실질로 분류
                표현 → 진행자가 수정(재검토 없음), 조립 → 진행자가 고쳐 재등록·재검토,
                실질 → [사용자 승인] 후 해당 쟁점만 5단계로 재개
                → [사용자: 최종 확정]
```

### 단계별 보충

**0. 준비**: 두 AI는 대화 맥락을 모른다. 진행자가 정리한 주제·배경·요구사항이 전부이므로 사용자가 시작 전에 확인한다. 요구사항은 영구 목록으로 저장해 모든 라운드에 넣는다.

**2. 쟁점표 초안**: 진행자는 쟁점의 제목과 판단할 질문만 쓰고 양측 입장은 쓰지 않는다. 비슷해 보이는 내용은 합의로 확정하지 않고 "합의 후보"로만 올린다. 한쪽만 언급한 내용은 곧바로 이견으로 보지 않고 "한쪽만 다룬 항목"으로 올린다.

**3. R2**: 쟁점표 이의와 실질 반박을 구분한다. 쟁점 표현을 먼저 확인하고, 유효한 쟁점에만 입장과 반박을 쓴다. 한쪽만 다룬 항목은 상대 AI만 분류한다.

**4. 쟁점표 확정**: 사용자 확인의 목적을 구분한다. 2단계 확인은 논의 범위 승인이고, 4단계 확인은 양측 이의를 반영한 기준 승인이다.

**5. R3 이후**: 상대 반박에 대한 응답을 의무로 한다(어떤 반박에 답하는지, 수용·반박과 근거, 유지·수정·철회). 쟁점 표현이 바뀌었으면 기존 반박이 아직 유효한지 먼저 밝힌다. 새 쟁점은 바로 공방에 넣지 않는다. 결론에 미치는 영향은 제안한 AI가 쓰고, 진행자는 중복만 정리하며, 추가 여부는 사용자가 라운드 판정 때 정한다.

**교착**: 승패나 합의로 처리하지 않는다. 스크립트는 교착 후보로 표시만 하고, 사용자가 추가 공방 / 보류 / 판정 중에서 고른다.

**6. 최종안**: 진행자는 조립만 하고 새 결론을 더하지 않는다. 각 결론에 출처 항목 ID를 붙인다. 표현 지적은 다시 검토하지 않고 반영한다. 실질 지적은 사용자 승인을 받아 해당 쟁점만 다시 연다.

### 사용자가 멈춰서 확인하는 지점

시작 승인, 논의 범위 승인, 기준 승인, 매 라운드 판정, 최종 확정, 그리고 실질 지적이 나왔을 때의 재개 승인. 새 쟁점 승인과 교착 처리는 라운드 판정에 묶어 따로 멈추지 않는다.

### 사용자 판정 예

| 사용자 말 | 처리 |
|---|---|
| "다음 라운드" | 미해결 쟁점으로 다음 라운드 |
| "쟁점 2는 Codex 쪽으로" | 쟁점 2를 Codex 입장으로 확정 |
| "쟁점 3은 둘 다 아니고 X로" | 쟁점 3을 사용자 결론 X로 확정 |
| "쟁점 1은 비용도 고려해서 다시" | 쟁점 1에 의견을 붙여 다음 라운드 |
| "예산은 월 10만 원 이하로" | 요구사항 목록에 추가 (이후 계속 적용) |
| "쟁점 하나 추가: ..." | 쟁점표에 추가 |
| "남은 건 전부 Claude 쪽으로" | 미해결 쟁점 전체를 한쪽으로 판정 |
| "최종안 써 줘" / "종료" | 6단계 / 판정 없이 종료 |

진행자는 사용자 문구를 고치지 않고 그대로 넘긴다.

## 항목 상태

| 상태 | 들어오는 경우 | 최종안 표시 |
|---|---|---|
| 논의 중 (`open`) | 쟁점 등록, 실질 지적으로 재개 | 최종 단계에는 남지 않음 |
| 합의 (`agreed`) | 합의 후보 양측 확인, 한쪽 항목에 상대 동의, 쟁점 철회·수용 | 결론으로 반영 |
| 사용자 판정 (`user_decided`) | 사용자가 결론을 정함 | 결론으로 반영, "사용자 판정" 표시 |
| 교착 후보 (`stall_candidate`) | 2연속 유지, 진행자·AI가 사유를 적어 표시 | 사용자가 처리할 때까지 유지 |
| 보류 (`deferred`) | 사용자가 보류 선택, 최대 라운드 도달 | "미해결"로 명시, 양측 입장 병기 |
| 미확인 (`unverified`) | 한쪽 항목에 상대가 "근거 부족" | "미확인"으로 명시 |
| 제외 (`excluded`) | 한쪽 항목에 상대가 "무관", 사용자가 제외 선택 | 넣지 않음, 사유는 로그에 남김 |
| 표현 충돌 (`wording_conflict`) | 양측이 서로 다른 표현 수정안을 냄 | 사용자가 고를 때까지 유지 |

## 기본값

| 항목 | 기본값 |
|---|---|
| 교착 기준 | 양측이 2라운드 연속 "유지" |
| 새 쟁점 제한 | AI당 라운드마다 최대 2개 |
| 최종안 | 진행자 조립 → 두 AI 검토 → 사용자 확정 |
| 전체 채택 | "남은 쟁점 전부 한쪽으로" 단축 명령으로만 남김 |
| 최대 라운드 | 5 (R1, R2 포함) |

# 구현 계획

## 파일 구성

[common.md](common.md)의 파일 구성을 따른다. 판정 모드는 log.md에 진행자 쟁점표와 사용자 판정도 남긴다.

## state.json

```json
{
  "id": "20261026-1030_주제",
  "topic": "...", "background": "...",
  "requirements": [{"id": "Q1", "text": "예산 월 10만 원 이하", "round": 0}],
  "context_files": [], "workdir": null, "max_rounds": 5,
  "phase": "discussion", "round": 3,
  "items": {
    "I1": {
      "kind": "issue",
      "origin": "moderator",
      "text": "TTL을 고정할 것인가, 키별로 둘 것인가",
      "status": "open",
      "wording_changed_round": 2,
      "positions": {
        "claude": {"text": "...", "stance": "keep", "round": 3},
        "codex":  {"text": "...", "stance": "revise", "round": 3}
      },
      "last_rebuttal": {"claude": "...", "codex": "..."},
      "keep_streak": {"claude": 1, "codex": 0},
      "missing": {"claude": 0, "codex": 0},
      "stall_reason": null,
      "user_note": null,
      "resolution": null
    }
  },
  "proposals": [{"id": "N1", "by": "codex", "round": 3, "text": "...", "grounds": "...", "impact": "..."}],
  "final": {"version": 0, "draft": null, "reviews": {}}
}
```

- `phase`: `draft` → `r2` → `baseline` → `discussion` → `final` → `done`
- `kind`: `issue`(쟁점) / `agree_candidate`(합의 후보) / `one_sided`(한쪽만 다룬 항목, `owner`에 꺼낸 쪽)
- `resolution`: `{"by": "agreement | withdraw | user", "text": "...", "round": n}`

## AI 응답 형식

JSON 블록의 위치와 파싱은 [common.md](common.md)를 따른다.

**R1**: JSON 없음. 독립 답변만.

**R2**
```json
{
  "items": [
    {"id": "I1", "wording": "ok",
     "position": "...", "grounds": "...", "rebuttal": "상대 R1의 어떤 주장에 대한 반박인지 포함"},
    {"id": "I2", "wording": {"revise": "수정한 질문", "reason": "..."},
     "position": "(선택) 수정안 기준 입장"},
    {"id": "A1", "confirm": true, "note": "(선택) 동의하며 붙이는 전제·한정"},
    {"id": "A2", "confirm": false, "reason": "..."},
    {"id": "S1", "response": "agree | disagree | insufficient | irrelevant", "reason": "...",
     "note": "(agree일 때 선택)"}
  ],
  "missing_issues": [{"question": "...", "reason": "..."}]
}
```

**R3 이후**
```json
{
  "items": [
    {"id": "I1",
     "prior_rebuttal_valid": true,
     "responds_to": "상대 반박의 요지",
     "reply": "accept | counter", "grounds": "...",
     "stance": "hold | change | withdraw",
     "position": "(change일 때 필수, hold일 때 선택) 입장 문장 전체",
     "note": "(withdraw일 때 선택) 받아들이며 붙이는 전제·한정",
     "rebuttal": "(선택) 상대 현재 입장에 남은 차이나 문제",
     "stall": null}
  ],
  "new_issues": [{"question": "...", "grounds": "...", "impact": "결론에 미치는 영향"}]
}
```
- `stance`: `hold` = 주장 내용 유지(표현만 다듬었으면 다듬은 문장을 `position`에), `change` = 주장 내용 변경, `withdraw` = 상대 현재 입장을 받아들임.
- 프롬프트의 JSON 예시는 쟁점마다 실제로 써야 하는 필드만 보인다.
- `prior_rebuttal_valid`: 쟁점 표현이 바뀐 바로 다음 라운드에만 쓴다.
- `stall`: 사유를 적으면 교착 후보가 된다.
- `new_issues`: 최대 2개.

**최종안 검토**
```json
{
  "checks": {"agreements": "ok | problem", "user_decisions": "ok | problem",
             "unresolved_listed": "ok | problem", "no_new_conclusions": "ok | problem"},
  "points": [{"type": "wording | assembly | substance", "item": "I3", "problem": "...", "suggestion": "..."}]
}
```
- `wording`(표현): 뜻은 맞고 문장만 고친다 → `final-fix`, 재검토 없음
- `assembly`(조립): 토의 기록과 다르게 옮기거나 묶거나 결론을 더함 → 진행자가 고쳐 `final`로 재등록·재검토. 조립 지적이 남아 있으면 `final-fix`를 거부한다
- `substance`(실질): 토의 결론 자체를 다시 다퉈야 함 → 사용자 승인 후 `reopen`

**형식 검사**: 공통 검사([common.md](common.md)) 외에 미해결 항목 ID가 모두 있는지, 새 쟁점이 2개 이하인지 검사한다. 재시도 방식은 [common.md](common.md)를 따른다.

**재시도 실패 시 (이 모드의 규칙)**: 빠진 항목의 `missing`을 1 올리고 라운드를 마친다. JSON 블록 자체를 읽을 수 없으면 그 AI의 모든 미해결 항목을 누락으로 본다.

## 스크립트 자동 처리 (절차만)

| 조건 | 처리 |
|---|---|
| R2에서 합의 후보를 양측 모두 확인 | `agreed` |
| R2에서 합의 후보에 이의 | 쟁점(`issue`, `open`)으로 전환 |
| 한쪽 항목에 상대가 `agree` / `disagree` / `insufficient` / `irrelevant` | `agreed` / 쟁점 / `unverified` / `excluded`(사유 기록) |
| 한쪽이 표현 수정안 제출 | 진행자 반영 목록에 넣음 |
| 양측이 서로 다른 수정안 제출 | `wording_conflict` |
| 한쪽이 `withdraw` | 쟁점을 닫고 상대 입장을 결론으로 (`agreed`, by: withdraw) |
| 양측이 같은 라운드에 모두 `withdraw` | `stall_candidate` (서로 상대 안을 받아들인 상태) |
| `change` | `keep_streak` 초기화 |
| `hold` | `keep_streak` +1 (다듬은 문장이 있으면 입장 문장 갱신) |
| 양측 `reply: accept` (상호 수용), 이미 입장이 있던 양측이 모두 `change` (양측 수정), 또는 양측 모두 `rebuttal`을 비움 (남은 차이 없음) | 수렴 신호. 상태는 그대로 두고 진행자가 판단할 때까지 next를 막는다 |
| 합의 후보 확인·한쪽 항목 동의·철회에 `note` | `notes`에 저장. 쟁점표, R3 프롬프트, 최종 검토 프롬프트, 최종안 뼈대에 싣는다 |
| 양측 `keep_streak` ≥ 2 | `stall_candidate` (사유: 양측 2라운드 연속 유지) |
| `stall`에 사유 있음 | `stall_candidate` (사유 기록) |
| 같은 쪽 `missing` ≥ 2 | `stall_candidate` (사유: 응답 누락 반복) |
| 최대 라운드 도달 | 남은 `open`과 `stall_candidate`를 `deferred`로, 최종 단계로 |

## 진행자 입력

진행자는 JSON 파일을 써서 `edit` 명령으로 넘긴다. 스크립트가 형식을 검사하고 로그에 남긴다.

| 시점 | 내용 |
|---|---|
| R1 뒤 | `{"issues": [{"text"}], "agree_candidates": [{"text"}], "one_sided": [{"owner", "text"}]}` |
| R2 뒤 | 표현 수정 반영 `{"op": "revise", "id", "text", "source"}`, 빠진 쟁점 추가 `{"op": "add", "text", "source"}` |
| R3 이후 | 새 쟁점 중복 정리 `{"op": "merge_proposals", "ids": ["N1", "N2"], "text"}`, 응답 누락 표시 `{"op": "flag_missing", "id", "who", "reason"}`, 수렴 판단 `{"op": "converge", "id", "decision": "agree\|open", "text", "reason"}` |
| 최종 | `final-draft` 뼈대에 결론 절과 문장 연결을 채운 Markdown 파일. 각 결론 옆에 출처 항목 ID. 마지막 라운드에서 보류된 쟁점의 수렴 판단(`converge`)도 이 단계에서 한다 |

**수렴 판단**: 스크립트가 수렴 신호(상호 수용 / 양측 수정)를 붙인 쟁점만 판단한다. 두 입장이 같은 결론에 이르렀으면 `agree`로 닫는다(`agreed`, by: moderator, 사유 필수). 차이가 남았으면 `open`으로 계속한다. 결론 문안은 두 입장 문장 안에서만 쓰고 새 내용을 더하지 않는다. 판단이 맞는지는 최종안 검토에서 두 AI가 확인한다.

스크립트가 기계적으로 할 수 있는 항목 분류는 진행자에게 맡기지 않는다.

## 하위 명령

| 명령 | 쓰는 쪽 | 하는 일 |
|---|---|---|
| `start --spec spec.json` | 진행자 (사용자 승인 후) | 토의 폴더 생성, R1 실행. spec: 주제·배경·요구사항·참조 파일·최대 라운드 |
| `edit <id> --file ops.json` | 진행자 | 쟁점표 작성·수정 |
| `next <id>` | 진행자 (사용자 승인 후) | 다음 AI 단계 실행 (draft → R2, baseline → R3, discussion → 다음 라운드) |
| `judge <id> <항목> claude\|codex\|--text "..."` | 사용자 판정 | 쟁점 판정 후 닫음 |
| `judge-all <id> claude\|codex` | 사용자 판정 | 미해결 쟁점 전체를 한쪽으로 |
| `note <id> <항목\|all> "..."` | 사용자 의견 | 다음 라운드에 붙일 의견 (원문 그대로) |
| `req <id> "..."` | 사용자 의견 | 요구사항 추가 (이후 계속 적용) |
| `defer <id> <항목>` | 사용자 판정 | 보류 |
| `exclude <id> <항목> ["사유"]` | 사용자 판정 | 제외 (최종안에 넣지 않음, 사유는 로그). 쟁점표 확정·공방 단계 |
| `pick-wording <id> <항목> claude\|codex` | 사용자 판정 | 표현 충돌 해결 |
| `proposal <id> <N번호> accept\|reject` | 사용자 판정 | 새 쟁점 승인·거절 |
| `final <id> --file draft.md` | 진행자 | 최종안 등록, 두 AI 검토 실행 |
| `final-draft <id>` | 진행자 | 최종안 뼈대(`final_draft.md`) 생성. 합의 / 사용자 판정 / 미해결 / 미확인 / 제외 절, 출처 ID·단서 포함 |
| `final-fix <id> --file draft.md` | 진행자 | 표현 지적만 반영 (재검토 없음). 조립 지적이 있으면 거부 |
| `reopen <id> <항목>` | 사용자 승인 | 실질 지적 쟁점을 다시 열고 discussion 단계로 |
| `confirm <id>` / `end <id>` | 사용자 | 최종 확정 / 판정 없이 종료 |
| `show <id>` | 진행자 | 현재 쟁점표와 쓸 수 있는 명령 출력 (세션 재개용) |

- `<id>`에는 토의 이름, `last`(가장 최근 토의), 이름 앞부분(하나만 맞을 때)을 쓸 수 있다.
- 모든 명령은 끝에 현재 쟁점표와 지금 phase에서 쓸 수 있는 명령을 출력한다. AI 단계 뒤에는 처리 결과와 원문 경로(`discussions/<id>/raw/...`)도 출력한다.
- 지금 phase에서 쓸 수 없는 명령은 거부한다.
- AI를 부르는 명령(`start`, `next`, `final`)은 스킬에서 백그라운드로 실행한다. 한 명령은 한 단계만 처리하므로 AI 호출은 동시 2번(재시도 포함)이다.

## 단계별 프롬프트 내용

| 단계 | 공통 | 단계별 |
|---|---|---|
| R1 | 주제, 배경, 요구사항, 참조 파일 | 독립 답변 요청 |
| R2 | 위와 같음 | 자기 R1, 상대 R1, 쟁점표 초안 |
| R3 이후 | 위 + 합의점과 확정된 결론 | 미해결 쟁점별 양측 현재 입장, 상대 최신 반박, 표현 변경 여부, 사용자 의견 |
| 최종 검토 | 위 + 전체 쟁점표(상태·결론·사용자 판정) | 최종안 |

## 구현하며 정한 것 (2026-10-26)

계획에 정해지지 않았던 부분을 구현하면서 아래처럼 정했다.

- `phase`의 `r2`는 두지 않았다. 쟁점표 초안을 넘긴 뒤 R2를 기다리는 동안 따로 할 명령이 없어서 `draft`에서 바로 `next`로 R2를 실행한다.
- 라운드 번호: R1=1, R2=2, 공방은 3부터. `max_rounds`의 최소값은 3이다.
- 교착 후보의 "추가 공방"은 `reopen`으로 한다(교착 후보·보류 → 논의 중, 맞선 횟수·누락 초기화). `next`는 논의 중(`open`) 쟁점만 공방한다.
- `final`을 부를 때 남은 논의 중·교착 후보·표현 충돌 항목은 보류(`deferred`)로 옮긴다. 최종안에 출처 ID가 빠진 결론 항목이 있으면 경고만 한다.
- 최종안을 등록한 뒤 `judge`·`reopen`으로 결론이 바뀌면 등록된 최종안을 내리고 다시 `final`을 받는다.
- 최대 라운드 뒤 `reopen`하면 한 라운드를 더 하고, 그 라운드가 끝나면 남은 쟁점은 다시 보류된다.
- 철회(`withdraw`)만 쟁점을 닫는다. `reply: accept`는 상대 반박을 받아들였다는 기록일 뿐 종료 조건이 아니다(스크립트 자동 처리 표를 따름).
- 합의 후보에 이의가 나오거나 한쪽 항목에 상대가 반대하면, 그 이유를 이의를 낸 쪽의 첫 반박(`last_rebuttal`)으로 넣는다. ID(A·S 번호)는 바꾸지 않는다.
- R2 재시도 실패로 응답이 빠지면: 쟁점은 누락 +1, 합의 후보·한쪽 항목은 확인을 못 받았으므로 쟁점으로 바꾸고 누락 +1.
- 입장이 아직 없는 쟁점(R2 뒤 새로 쟁점이 된 것)에서는 `keep`을 쓸 수 없고 `revise`로 입장을 적는다. 상대 입장이 없으면 `withdraw`를 쓸 수 없다.
- 진행자 입력 검사: 표현 수정(`revise`)은 AI 수정안이 있는 쟁점에만, 쟁점 추가(`add`)는 빠진 쟁점 제안(M 번호)을 출처로 적을 때만 받는다. 수정안·제안이 반영되지 않았거나 표현 충돌이 남아 있으면 R3을 시작하지 않는다(거절 불가 원칙).
- 예전 방식의 명령과 대화형 메뉴는 두지 않았다. 모든 진행은 하위 명령으로 한다.
- 사용자가 쟁점을 논의 범위에서 빼는 `exclude`를 추가했다(2026-10-26, 탕수육 토의에서 "쟁점 1, 2만 남기고"를 처리하려고). 보류와 달리 최종안에 넣지 않는다.

## 실사용 피드백 반영 (2026-10-26, 탕수육 토의)

탕수육 부먹·찍먹 토의를 실제 CLI로 진행한 뒤 아래를 바꿨다.

- 진행자는 AI 본문을 채팅에 옮기지 않는다. 쟁점표(입장·최신 반박·처리 결과)와 원문 링크만 보인다. 본문 전체와 쟁점표가 같은 내용을 두 번 실어 답변이 너무 길었다.
- 수렴 신호와 진행자의 `converge` 판단을 추가했다. I1은 양측이 서로의 반박을 수용하고 입장을 고쳤는데도, 쟁점을 닫는 방법이 철회뿐이라 닫히지 않았다.
- 합의 후보 확인·한쪽 항목 동의·철회에 `note`(단서)를 추가했다. A4에 붙인 단서가 저장되지 않아, 최종 검토에서 "출처 확인 불가" 지적이 두 번 나왔다.
- `final-draft` 뼈대를 추가했다. 진행자가 합의에 없던 분류 소제목을 붙여 실질 지적을 받았다.
- 검토 지적에 `assembly`(조립)를 추가했다. 조립 문제를 실질 지적으로 받아 재개 규칙에 맞지 않았다.
- `keep`/`revise`를 `hold`/`change`로 바꿨다. Claude가 "표현만 다듬는다"며 `keep`을 써서, 다듬은 문장이 버려졌다.
- 토의 이름을 `YYYYMMDD-HHMM_슬러그(10자)`로 줄이고(spec의 `name`으로 지정 가능), `last`와 앞부분 일치를 추가했다.
- 빠진 쟁점 제안은 그대로 둔다(거절 불가). 이번에 I3~I5를 뺀 것은 사용자의 임의 판단이었다.
- 이름을 '토론'에서 '토의'로 바꿨다. 실제로 돌려 보니 두 AI가 이기고 지는 것이 아니라, 어디까지 같은 생각인지 좁혀 가는 방식으로 움직였다. 바꾼 범위는 사용자에게 보이는 문구, 문서, AI 프롬프트다. 파일·폴더·명령·JSON 필드 이름은 그대로 둔다.
  - 나중에(2026-10-26) 파일·폴더·코드 이름과 phase 값도 `debate`에서 `discussion`으로 바꿨다(`discussion.mjs`, `discussions/`). `rebuttal` 등 다른 필드 이름은 그대로다.
  - 프롬프트: "토론한다"를 "함께 토의해 결론을 찾는다"로 바꿨다. 반박(`rebuttal`)은 "상대 입장에 남은 차이나 문제"로 바꾸고 선택으로 했다.
  - 비워 둔 지적은 해소된 것으로 보아 `last_rebuttal`에서 지운다. 양측이 모두 비우면 "남은 차이 없음" 수렴 신호가 붙는다.

## 실행 환경 (2026-10-26)

스크립트는 `discussion.mjs` 파일 하나이고, Node.js 18 이상만 있으면 된다(외부 패키지 없음). Codex CLI를 npm으로 설치했다면 Node.js가 이미 있다.

- 기록 파일은 LF로 쓴다. 읽을 때는 CRLF로 저장된 파일도 받는다.
- Windows에서 npm으로 설치한 CLI(`codex.cmd` 등)는 cmd.exe를 거쳐 실행하고, 인자는 따옴표로 감싼다.
- 시간 제한은 직접 타이머로 건다. `spawn`의 `timeout` 옵션은 CLI를 찾지 못했을 때 타이머가 남아 프로세스가 10분 동안 끝나지 않았다.
- 검증: dry-run 시나리오(자동 합의 7개, 판정 8개)를 명령 427개로 돌려 모든 단계·명령의 성공·오류 경로를 확인했다. 실제 CLI로는 R1 한 단계(작업 폴더 경로에 공백 포함)를 확인했다.
