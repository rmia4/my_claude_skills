# AI 자동 합의 모드: 순차 토의 흐름

- 상태: 계획 확정, 미구현 (2026-10-26, 같은 날 피드백 반영)
- 범위: AI 자동 합의 모드. 사용자 판정 모드는 [judge-mode-flow.md](judge-mode-flow.md)를 따른다.
- 공통 규칙(파일 구성, 응답 파싱, 재시도, 호출 실패, 저장·재개, dry-run)은 [common.md](common.md)를 따른다. 이 문서에는 이 모드에만 해당하는 규칙을 적는다.

## 방식

한 AI(X)가 초안을 쓰고 다른 AI(Y)가 검토하는 순차 토의다. 지적과 수정을 되풀이하다가 남은 지적이 없으면 끝난다.

순차 토의의 가장 큰 약점은 첫 의견의 영향력이 크다는 점이다. 이를 줄이려고 다음 세 가지를 반영한다.

| 보완 | 막는 문제 | 내용 |
|---|---|---|
| A. 독립 R1 | Y의 생각이 X의 안에 고정됨 | 초안을 쓰기 전에 두 AI가 상대 안을 보지 않고 동시에 각자 답한다 |
| B. 판단 기준 합의 | X가 문제 정의와 판단 기준을 선점함 | R1에서 각자 판단 기준을 적는다. 초안은 양쪽 기준을 합친 목록으로 평가하며, 기준을 빼거나 합치려면 이유를 적는다 |
| E. 대체안 제시권 | X가 표현을 독점함 | 검토자는 지적만 하지 않고 대체 문안을 낼 수 있다 |

검토했으나 반영하지 않은 보완: 채택 대장, 역할 교대, 미해결 병기, 순서 바꿔 재실행, 작성자 익명화, 핵심 주장 추적.

## 역할

| 주체 | 맡는 일 |
|---|---|
| 사용자 | 시작 내용 승인. 이후에는 결과만 받는다 |
| 진행자 (토의를 호출한 Claude Code 세션) | 주제·배경·요구사항 정리, 단계 실행, 결과를 원문 그대로 보고. 판단은 하지 않는다 |
| 스크립트 (discussion.mjs) | AI 호출, 상태 저장, 응답 파싱, 지적 상태 전이, 합의·종료 판정, 로그 기록 |
| X (첫 초안 작성자) | 통합 초안 작성, 지적에 수용·반박, 초안 수정. 끝까지 작성자 |
| Y (검토자) | 판단 기준에 비춰 검토, 지적·대체 문안 제시. 끝까지 검토자 |

X는 토의마다 Claude와 Codex가 번갈아 맡는다("통합안은 번갈아 작성하고 반대쪽이 승인한다"는 처음 결정을 따름). 누가 X였는지는 상태 파일과 결과 보고에 남긴다.

## 진행 흐름

```
0. 준비    진행자: 주제·배경·요구사항 → [사용자: 시작 승인] → start --mode consensus
1. R1      두 AI 독립 답변 (동시): 답 + 판단 기준 목록                     [A, B]
2. 초안    X: 두 R1을 바탕으로 통합 초안
           · 초안 첫머리에 "판단 기준" = 양측 기준을 합친 목록
           · 기준을 빼거나 합치면 이유 명시                                  [B]
3. 검토    Y (라운드 1): 판단 기준에 비춰 초안 검토
           · 새 지적 최대 5개: 문제, 근거, 해당 기준. 지적할 것은 이번에 모두 낸다
           · 기준 처리(제외·병합)에 이의가 있으면 이것도 지적으로 올림        [B]
           · 필요하면 대체 문안 제시                                         [E]
4. 수정    X: 모든 open 지적에 수용 / 반박 → 수정된 초안 전체 제출
5. 재검토  Y: 모든 accepted·rebutted 지적에 응답
           · accepted → 반영 확인(confirm) / 반영 부족(keep)
           · rebutted → 철회(withdraw) / 유지(keep)
           · 새 지적 최대 2개 (마지막 라운드에는 금지)
             직전 수정에서 바뀐 절과 그 영향만 대상(scope: changed).
             원래 있던 내용을 놓친 지적은 scope: missed + 놓친 이유
   ↺ 4~5 반복 (라운드 2부터 라운드 하나 = 수정 + 재검토)
6. 종료    스크립트가 지적 상태로 판정 (아래 "종료 판정")
7. 보고    진행자: 결과 보고 (아래 "결과 보고")
```

"a 동의 → b 동의 → 끝"과의 대응: X가 수정본을 내는 것이 a의 동의이고, Y가 모든 지적을 종료하고 새 지적 없이 승인하는 것이 b의 동의다.

## 지적 상태와 전이

### 상태

| 상태 | 뜻 | 다음에 응답할 쪽 |
|---|---|---|
| `open` | 새 지적이거나 Y가 유지한 지적 | X |
| `accepted` | X가 수용함 | Y |
| `rebutted` | X가 반박함 | Y |
| `closed` | 종료. 종료 방식 `applied`(반영) 또는 `withdrawn`(철회) | 없음 |

### X의 응답 (`open` 지적에만)

| 현재 | X 응답 | 다음 상태 | 맞선 횟수 |
|---|---|---|---|
| open | `accept` + `as_is` | accepted | 0으로 초기화 |
| open | `accept` + `modified` (사유 필수) | accepted | 0으로 초기화 |
| open | `rebut` (근거 필수) | rebutted | 그대로 |

### Y의 응답 (`accepted`·`rebutted` 지적, 그리고 새 지적)

| 현재 | Y 응답 | 다음 상태 | 맞선 횟수 |
|---|---|---|---|
| accepted | `confirm` | closed (applied) | — |
| accepted | `keep` (반영이 부족한 근거 필수) | open | 그대로 |
| rebutted | `withdraw` (철회 근거 필수) | closed (withdrawn) | — |
| rebutted | `keep` (재반박 필수) | open | +1 |
| (없음) | `new` (문제·근거 필수) | open | 0 |

### 허용하지 않는 조합 (형식 오류)

- 상태에 맞지 않는 응답. 예: accepted 지적에 `withdraw`, rebutted 지적에 `confirm`, X가 accepted 지적에 응답
- 종료된 ID, 존재하지 않는 ID
- 같은 ID에 두 번 응답
- 응답해야 할 ID를 빠뜨림
- 새 지적 개수 초과, 마지막 라운드의 새 지적
- 라운드 2 이후 새 지적에 `scope`가 없거나, `missed`인데 놓친 이유(`reason`)가 없음

수정이 새 문제를 만들었으면 같은 ID에 `keep`으로 답하거나 `new`로 새로 지적한다. 종료된 지적을 다시 다투려면 `new`로 올린다.

### 지적 ID

- 새 지적의 ID는 스크립트가 붙인다(P1, P2 … 순서대로, 재사용하지 않음). Y는 새 지적의 `id`를 `null`로 적는다.
- 다음 단계 프롬프트에는 스크립트가 붙인 ID로 지적 목록을 보여 준다.
- 같은 문제를 가리키는 지적을 합치는 기능은 두지 않는다. X가 "P2와 중복"이라고 반박하고 Y가 철회하는 일반 절차로 처리한다.

### 교착

- 맞선 횟수는 "X 반박 → Y 유지" 한 번의 왕복마다 1씩 올라가고, X가 수용하면 0으로 돌아간다.
- 맞선 횟수가 2 이상인 `open` 지적을 교착으로 표시한다.
- 교착 지적도 계속 응답해야 한다. 다음 라운드에 X가 수용하면 교착에서 풀린다.

## 필수 응답 범위

| 단계 | 응답자 | 반드시 응답할 지적 | 새 지적 |
|---|---|---|---|
| 검토 (라운드 1) | Y | 없음 | 최대 5개 |
| 수정 | X | 모든 `open` | 불가 |
| 재검토 (라운드 2~4) | Y | 모든 `accepted`, `rebutted` | 최대 2개. `scope` 필수 |
| 재검토 (마지막 라운드) | Y | 모든 `accepted`, `rebutted` | 금지 |

## 종료 판정

합의 여부는 **스크립트가 지적 상태로 판정**한다. Y의 `approve`는 이 판정과 맞는지 확인하는 용도로만 쓴다.

| 시점 | 조건 | 결과 |
|---|---|---|
| Y 응답 적용 후 | `closed`가 아닌 지적 0개, `approve: true` | **합의** |
| Y 응답 적용 후 | `closed`가 아닌 지적이 있는데 `approve: true` | 형식 오류 |
| Y 응답 적용 후 | `closed`가 아닌 지적 0개, 새 지적도 없는데 `approve: false` | 형식 오류 |
| X 수정 차례 직전 | 남은 지적이 모두 교착 | **합의 실패** (조기 종료) |
| 마지막 라운드 재검토 후 | `closed`가 아닌 지적이 있음 | **합의 실패** (최대 라운드) |

라운드 1 검토에서 Y가 지적 없이 `approve: true`를 내면 초안 그대로 합의다.

## 라운드 경계 예시 (최대 라운드 5)

```
준비     R1 (두 AI 동시) → 초안 (X)
라운드1  검토 (Y)                       새 지적 최대 5개
라운드2  수정 (X) → 재검토 (Y)           새 지적 최대 2개
라운드3  수정 (X) → 재검토 (Y)           새 지적 최대 2개
라운드4  수정 (X) → 재검토 (Y)           새 지적 최대 2개
라운드5  수정 (X) → 재검토 (Y)           새 지적 금지
         → 남은 지적이 있으면 여기서 합의 실패
```

재시도를 빼면 호출은 최대 12번이다(R1 2번, 초안 1번, 검토 1번, 라운드 2~5의 수정·재검토 8번).

## 응답 형식

JSON 블록의 위치와 파싱은 [common.md](common.md)를 따른다.

**R1** (두 AI 각자)
```json
{"criteria": ["비용", "운영 부담", "확장성"]}
```

**초안** (X): JSON 없음. 본문 첫머리에 합친 판단 기준과 제외·병합 사유를 적는다.

**검토 / 재검토** (Y)
```json
{
  "points": [
    {"id": null, "action": "new", "problem": "...", "grounds": "...", "criterion": "비용",
     "replacement": {"target": "바꿀 부분 인용", "text": "대체 문안"}},
    {"id": "P2", "action": "keep", "grounds": "재반박 또는 반영이 부족한 근거"},
    {"id": "P3", "action": "withdraw", "grounds": "X의 반박 중 어떤 근거로 철회하는지"},
    {"id": "P4", "action": "confirm"}
  ],
  "approve": false
}
```
- `criterion`: 해당 판단 기준. 기준 처리 자체에 대한 이의면 그 기준 이름을 적는다.
- `replacement`: 선택.
- `scope`: 라운드 2부터 새 지적에 필수. 재검토 프롬프트에는 직전 수정에서 바뀐 절 목록(제목 단위로 비교)이 들어간다. 바뀐 부분이나 그 영향이면 `changed`, 1라운드에 냈어야 할 지적이면 `missed`와 `reason`(놓친 이유). `missed`는 막지 않고 로그와 결과 보고에 남긴다.

**수정** (X): 본문은 수정된 초안 전체.
```json
{
  "responses": [
    {"id": "P1", "reply": "accept", "applied": "as_is"},
    {"id": "P5", "reply": "accept", "applied": "modified", "reason": "..."},
    {"id": "P2", "reply": "rebut", "grounds": "..."}
  ]
}
```

## 대체 문안

- 스크립트는 대체 문안을 직접 넣지 않는다. X가 수정본 전체를 다시 쓸 때 반영한다.
- `target`은 어느 부분인지 알려 주는 단서일 뿐이다. 정확한 위치 지정은 요구하지 않는다.
- 반영이 맞는지는 Y가 `confirm` 또는 `keep`으로 확인한다.

## 합의의 의미

- **합의**는 최종 초안 전체에 대해 양측이 동의했다는 뜻이다.
- 지적별로는 종료 방식이 다르다. **반영**(`applied`)은 X가 Y의 지적을 받아들인 것이고, **철회**(`withdrawn`)는 Y가 양보한 것이다. 철회는 같은 의견에 이른 것으로 기록하지 않고 결과 보고에서 따로 보여 준다.

## 재시도 실패 시 (이 모드의 규칙)

- 형식 오류 재시도가 실패하면 `status: halted`로 멈춘다([common.md](common.md)의 재개 규칙을 따름).
- 사용자 판정 모드처럼 누락으로 세고 넘어가지 않는다. 자동 모드에서 응답이 빠지면 지적 상태 전이가 끊기기 때문이다.

## 결과 보고

원문 표시 범위는 [common.md](common.md)를 따른다(채택된 시도의 본문만).

| 결과 | 보고 내용 |
|---|---|
| 합의 | 최종 초안(`final.md` 링크), 판단 기준, 지적마다 종료 방식(반영 / 고쳐 반영 / 철회) |
| 합의 실패 | 마지막 초안(`final.md` 링크), 남은 지적마다 X의 마지막 응답과 Y의 마지막 응답(스크립트 출력 그대로), 실패 사유(최대 라운드 / 전부 교착) |
| 중단(오류) | 중단된 단계, 오류 내용, 재개 방법 |
| 공통 | 첫 작성자, 철회된 지적 수와 각 철회 근거, 라운드 2 이후 놓친 지적(`missed`) 목록 |

## 이 조합에서 남는 성질

반영하지 않은 보완책 때문에 남는 성질이다. 이번에 택하지 않은 범위로 기록한다.

- 작성 권한은 X에게 계속 있다(역할 교대 없음). Y의 표현은 대체 문안으로 들어간다.
- Y의 R1 중 X가 초안에서 뺀 내용은 Y가 지적해야 살아난다(채택 대장 없음). **Y가 놓친 R1 항목은 결과에 반영되지 않으며, 그 때문에 결론이 달라질 수 있는 위험을 감수한다.**
- 결과는 합의 또는 합의 실패 둘뿐이다(미해결 병기 없음, 부분 합의 없음).
- 근거의 질은 검사하지 않는다. 빈 근거만 형식 오류로 막는다.

## 구현 메모

- 진행자는 판단할 일이 없다. `start` 뒤에 `run`을 한 번 부르면 스크립트가 종료나 중단까지 `next`를 이어서 실행한다. `run`의 종료 코드는 종료(합의·합의 실패) 0, 중단 1이다. 판정 모드에서는 쓸 수 없다.
- 각 단계는 AI 호출 1번이다(R1만 동시 2번). `run`은 10~20분 걸리므로 스킬에서는 백그라운드로 실행한다.
- 전체 답변을 되풀이하다 `{"agree"}` 하나로 판정하는 방식은 쓰지 않는다. 지적 단위로 상태를 관리한다.
